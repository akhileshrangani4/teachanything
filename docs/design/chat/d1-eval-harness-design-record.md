````text
# Retrieval and answer eval

An offline measure of what a chat turn retrieves and how the model uses it, so
a retrieval or prompt change is judged by numbers. Two modes:

| Mode | Command | Needs | Deterministic |
| --- | --- | --- | --- |
| Retrieval | `npm run eval:retrieval -w apps/web` | Postgres with pgvector | Yes (latency aside) |
| Answers | `npm run eval:answers -w apps/web` | Postgres, `OPENROUTER_API_KEY`, `OPENAI_API_KEY` | No: answers are sampled |

Neither runs in CI. The scoring logic is in `src/server/eval/` and its unit
tests (`src/__tests__/server/eval/`) do run in CI with `npm run test`.

## Scratch database

Both runners take `TEST_DATABASE_URL`, apply the app's migrations to it and
write fixture rows, so they refuse any URL whose database name doesn't contain
`test` or `eval`. They exit non-zero before touching anything when it is unset.

```bash
createdb teachanything_eval
psql teachanything_eval -c 'CREATE EXTENSION IF NOT EXISTS vector'
export TEST_DATABASE_URL=postgres://user:pass@localhost:5432/teachanything_eval
```

The fixtures load once and are reused while the corpus, embeddings and chatbot
settings are unchanged; a change is detected by fingerprint and reloads them.

## Retrieval mode

For each golden case it calls the production `buildRAGContext` (and through
it `hybridSearch`) with the chunk limit a real turn on the default chatbot
would get, then scores what was injected. Only the latest question is sent to
retrieval, as production does today, so follow-up cases measure that.

Query and chunk embeddings come from `fixtures/embeddings.json`, so this mode
needs no API key. When the cache lacks a text, the runner fills it if
`OPENAI_API_KEY` is set; otherwise it stops and names every missing text hash.

| Metric | Meaning |
| --- | --- |
| recall@injected | Share of answerable, exact and follow-up cases where an expected passage was injected |
| MRR | Mean of 1 / rank of the first expected passage in the injected list (0 when missing) |
| off-topic false injection | Share of off-topic cases that injected any passage |
| page accuracy | Share of hits with a page anchor whose passage carries that page |
| injected tokens | Median and p95 over all cases, as the pipeline counts them |
| latency | p50 and p95 of `buildRAGContext`, after one warm-up search |

Each run writes `reports/retrieval-<timestamp>.json` and a markdown summary
(ignored by git). Every case records a hash of its ranked chunk list, so two
runs can be diffed case by case, not just by summary.

### Regression gate

```bash
npm run eval:retrieval -w apps/web -- --compare eval/baseline.json
```

exits 1 when any of these moves past its tolerance from the baseline:

| Metric | Fails when |
| --- | --- |
| recall@injected | drops by more than 0.03 |
| MRR | drops by more than 0.03 |
| off-topic false injection | rises by more than 0.05 |
| injected tokens, median and p95 | grow by more than 10% |

Latency is reported but not gated; it depends on the machine.

`baseline.json` is a retrieval report from a clean commit. To move it, run the
eval on the commit that changes behavior and copy that report over it in its
own commit, quoting the old and new summaries in the PR.

## Answer mode

Runs every golden case through the production chat turn (`streamChat`) on the
default chatbot's model, with follow-up history seeded into the conversation,
then scores the persisted answer and sources. Retrieval tool calls embed their
queries live, which is why this mode also needs `OPENAI_API_KEY`.

```bash
npm run eval:answers -w apps/web -- --concurrency 4
```

| Metric | Meaning |
| --- | --- |
| citation rate | Share of answers with at least one `[n]` marker |
| citation validity | Among answers with markers, share citing only refs they were given |
| cited-source precision | Per answerable case, the share of cited passages that match a golden anchor; averaged over cases |
| shown-source precision | The same for every source the turn persisted, i.e. what a student sees with sources on |
| denial rate on answerable | Share of answerable, exact and follow-up cases where the answer says the materials don't cover it |
| off-topic decline rate | Share of off-topic cases the model declined as outside the materials |

Refs are numbered in the order the turn persisted its sources. Until passages
are numbered in the prompt, models don't emit `[n]`, so the citation metrics
read `n/a`.

Denials are detected by phrase (`isDenial`), tested against answers recorded
from the default model. A new phrasing that slips through undercounts both
denial rates; add it to the patterns and the recorded-answer tests.

## Known limits

- The corpus is 126 chunks (about 23.6k tokens). On the default model a turn
  can inject most of it, so recall@injected is near 1 by construction. MRR,
  injected tokens and off-topic false injection discriminate better at this
  size.
- `pdf-parse` 1.1.1 joins PDF pages with blank lines, but the page-aware
  chunker splits on form feeds, so every PDF chunk is stored as page 1. Page
  accuracy is therefore 0 today. Anchors match on file and text only, so
  fixing extraction will move page accuracy without moving recall.
````

```text
## Why these three

- Two PDFs with 12–16 pages each exercise page numbers. The Markdown file
  exercises the no-page path.
- Two subjects that share no vocabulary, plus two economics documents that share
  a lot (demand curves appear in both), so retrieval has to tell neighbouring
  passages apart rather than just pick the right subject.
- 126 chunks in total, under the 300-chunk ceiling, so a full run stays fast.

## Files

- `corpus.json` — the manifest: file name as the app shows it, path, MIME type.
- `golden.json` — the golden cases. See `src/server/eval/golden.ts` for the
  schema and the consistency rules the loader enforces.
- `embeddings.json` — generated: the embedding of every chunk and golden query,
  keyed by a hash of the text. Either runner embeds any text the cache lacks
  when `OPENAI_API_KEY` is set and writes it back here; without the key it
  stops and lists the missing hashes. Commit the regenerated file in its own
  commit; never edit it by hand.

## Writing golden anchors

An expected passage is `{ fileName, pageNumber?, mustContain }`. `mustContain`
is a short quote from the source (at most 140 characters) and must appear in
the chunk text. Matching ignores case, whitespace, typographic quotes and dashes,
because `pdf-parse` drops the space where the font changes around a bold term
("called anormal good"). `pageNumber` is the page of the fixture file, counted
from 1, not the printed page number of the book.

Anchors match on file and text only; the page is scored separately as page
accuracy. Today's PDF extraction tags every chunk as page 1 (`pdf-parse` joins
pages with blank lines, not the form feeds the page-aware chunker splits on), so
baseline page accuracy is low by construction. Keeping the page out of the
match means fixing that later changes page accuracy, not recall.

The runner refuses to score while any anchor matches no chunk, so a typo or a
chunker change shows up as an error rather than a silent miss.
```
